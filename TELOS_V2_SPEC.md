## READ THIS BEFORE STARTING

**Hard prerequisite: the Postgres migration must be complete and verified.**
Do not begin Phase 1 until all of these are true:

- `migrate_to_postgres.py` has run against Neon and per-table row counts match SQLite exactly
- The app boots locally against the pooler `DATABASE_URL` and every existing page renders
- Heatmap and stats figures have been diffed against the old SQLite values and agree
- Everything is committed and pushed

Building new schema on top of an unverified migration means debugging two things at
once. If the migration isn't done, stop and finish it.

**Working rules for this spec:**

1. One phase per branch, one phase per PR-sized commit. Branch names given per phase.
2. After each phase: boot the app, walk every page in the nav, confirm nothing 500s.
3. All schema changes go in numbered files under `migrations/` (`001_...sql`,
   `002_...sql`) with a small runner. Never hand-edit the DB.
4. Every migration must be idempotent (`IF NOT EXISTS`, `ON CONFLICT DO NOTHING`).
5. New paid features go behind a feature flag read from env
   (`FEATURE_PREDICTED_GRADE=1` etc.) so they can ship dark and be enabled per-env.
6. Never hardcode prices in templates. Read from a single `PRICING` dict in config.
7. Do not touch `db.py`, `migrate_to_postgres.py`, or `scan_sqliteisms.py`.
8. Postgres `LIKE` is case-sensitive. Every user-facing search uses `ILIKE`.
9. Ask before deleting or rewriting any existing user-facing route.

**Stop and ask me if:** a phase would require dropping a column that holds user data,
any existing user's tracked papers would become inaccessible, or the Stripe changes
would affect an existing subscriber's billing.

## Phase 2 — Access control

Branch: `feat/access-control`

In `auth.py` (create if absent):

```python
def user_is_pro(user) -> bool:
    """Single source of truth for paid access."""
    if user.grandfathered:
        return True
    if user.subscription_status not in ("active", "trialing", "past_due"):
        return False
    # grace: keep access until the paid period actually ends
    return user.current_period_end is None or user.current_period_end > utcnow()
```

`past_due` keeps access deliberately — a failed card should not lock a student out
mid-revision. Stripe retries for ~2 weeks; `canceled`/`unpaid` cut access.

Provide:
- `@requires_pro` decorator → redirects to `/subscription` with a flash naming the

  teaser state plus a CTA. **Never a bare 403.** A locked feature the user can see the

## Phase 3 — Predicted grade engine (the core feature)

Branch: `feat/predicted-grade`
New file: `prediction.py`. Pure functions, no Flask imports, so it's unit-testable.

This is the feature everything else hangs off. Build it carefully.

### Why not percentages

A 62% on a hard 2019 paper and a 62% on an easy 2023 paper are not the same
performance. You already have `grade_boundaries`, so use them: convert each attempt to
a position on a continuous grade scale, which normalises difficulty automatically.

### Algorithm

**Step 1 — grade points.** `A*=6, A=5, B=4, C=3, D=2, E=1, U=0`.

**Step 2 — per-attempt grade score.** For an attempt with `total_marks` on a paper
with known boundaries, linearly interpolate between the two boundaries it falls
between:

```
score = grade_point(lower) + (marks - lower_bound) / (upper_bound - lower_bound)
```

Above the A* boundary, cap at 6.0 plus a small bonus scaled by the remaining marks to
full (max 6.5). Below E, scale linearly down to 0.

If boundaries for that exact `(board, subject, paper_code, year)` are missing, fall
back in this order: same paper other years (use the median boundary set) → same
subject same year → skip the attempt entirely and note it. **Never invent boundaries.**

**Step 3 — recency-weighted mean.** Recent papers matter more:

```
weight_i = 0.85 ** i        # i = 0 for most recent, ordered by taken_at DESC
grade_score = Σ(w_i · score_i) / Σ(w_i)
```

**Step 4 — predicted grade.** Floor the grade score back to a letter.

**Step 5 — marks to next boundary.** Use the **most recent available year's**
boundaries for that subject (the best estimate of the next real exam). Compute the raw
mark corresponding to the current grade score, then:

```
marks_to_next = next_grade_boundary − equivalent_raw_mark
```

Round up, and express per paper. Present as: "You're 6 marks off an A."

**Step 6 — confidence.** Compute the weighted standard error of the grade scores.

| Sample size | Behaviour |
|---|---|
| 0–2 papers | **Do not show a prediction.** Show "Log 3 papers to unlock your predicted grade." |
| 3–4 | `confidence='low'`, show as a range ("B–A"), label "provisional" |
| 5–9 | `confidence='medium'` |
| 10+ | `confidence='high'` |

Also downgrade confidence one level if the standard error spans more than one grade,
regardless of sample size.

### Presentation — this matters

The number is going to be the most emotionally loaded thing in the product. Two rules:

1. **Always pair the prediction with the action.** Never show a bare grade. The unit is
   "You're a high B — 6 marks off an A, and 4 of those marks are in complex numbers."
   A prediction without a next step is just anxiety.
2. **Never show a downgrade as a headline.** If the prediction drops, lead with the
   trend and the recoverable marks, not "you have dropped from A to B."

Copy for low confidence: "Provisional — based on 3 papers. Log more for a sharper
estimate." Not a false-precision number.

### Recompute triggers

On paper insert/update/delete, and on question-attempt changes. Write to
`grade_predictions`. Read from cache everywhere else — do not recompute on page load.

### Tests

`tests/test_prediction.py`, covering: exact boundary hits; above A*; below E; missing
boundaries for a year; a single paper (must refuse to predict); improving trend
(recency weighting must move the number); identical raw marks across a hard and easy
year (must yield different grade scores — this is the whole point).

## Phase 4 — Prescription: "your next 3 questions"

Branch: `feat/prescriptions`

Turns the heatmap from information into instruction.

**Topic priority score:**

```
priority = marks_lost_ratio × log(1 + topic_frequency) × recency_factor
```

- `marks_lost_ratio` = 1 − (marks scored / marks available) for that topic
- `topic_frequency` = how often the topic appears across that subject's papers — a
  weak topic that shows up every year matters more than a weak rare one
- `recency_factor` = 1.3 if the last attempt was in the most recent 3 papers, else 1.0

Take the top 3 topics, then select from `bank_questions` matching those topics,
preferring unattempted questions, then ones scored below 60%. Return question, source
paper, and *why* it was picked ("you're at 41% on complex numbers, worth ~8 marks/paper").

The "why" line is not optional — an unexplained recommendation gets ignored.

Add a **Today** panel on the dashboard: predicted grade, 3 questions, due revision
count. This should be the reason someone opens the app daily.

## Phase 5 — Pricing and Stripe

Branch: `feat/pricing-v2`

### Prices

| Plan | Price | Stripe net (1.5% + 20p, +20% VAT on fees) |
|---|---|---|
| Monthly | **£4.99** | ~£4.66 |
| Annual | **£29** | ~£28.31 |
| Legacy monthly | £2 (grandfathered only) | ~£1.72 |

The 20p fixed fee is why £2 doesn't work: it eats ~14% of every payment. At £29/year
you keep ~98%.

Create both new prices in Stripe. **Keep the £2 price active** — do not migrate or
cancel any existing subscription. Grandfathered users stay at £2 indefinitely.

### Checkout UI

Annual is the **default selected option**. Show the comparison explicitly:
"£29/year — that's £2.42/month. Save £31 vs monthly."

Annual matters more than the headline price: A-level revision collapses in June when
Year 13 finish, so monthly billing gets you ~7 payments then permanent churn. Annual
captures the whole cycle up front.

Anchor the annual push around September and January (mock season).

### Implementation

- `POST /subscription/checkout` — creates a Stripe Checkout Session (`mode=subscription`),
  takes `interval` (`month`|`year`), sets `client_reference_id` to the user id,
  `success_url` / `cancel_url` back to `/subscription`
- `POST /stripe/webhook` — **must verify the signature** with
  `stripe.Webhook.construct_event` and `STRIPE_WEBHOOK_SECRET`. Reject unverified.
  Handle: `checkout.session.completed`, `customer.subscription.updated`,
  `customer.subscription.deleted`, `invoice.payment_failed`,
  `invoice.payment_succeeded`. Make handlers idempotent (Stripe retries) — key on
  event id, ignore ones already processed.
- `POST /subscription/portal` — Stripe Billing Portal so users self-serve
  cancellation. Do not build a custom cancel flow.
- Never grant Pro from the success redirect. **Only the webhook writes entitlements.**
  The redirect can be faked by hand.

Test with `stripe listen --forward-to localhost:5000/stripe/webhook` and the test-mode
card `4242 4242 4242 4242`. Test the full cancel → period-end → access-lost path with
Stripe's clock simulation before going live.

Env vars: `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY`, `STRIPE_PRICE_MONTHLY`,
`STRIPE_PRICE_ANNUAL`, `STRIPE_PRICE_LEGACY`, `STRIPE_WEBHOOK_SECRET`.

## Phase 6 — Spaced repetition

Branch: `feat/spaced-repetition`

SM-2 simplified. Any question scored below 60% enters `revision_queue` automatically.

Review outcome → interval:

| Outcome | Effect |
|---|---|
| Got it | `repetitions += 1`, interval → 1, 3, 7, 16, 35 days by repetition count, `ease += 0.1` |
| Partly | interval unchanged, `ease −= 0.15` |
| Missed | `repetitions = 0`, interval → 1 day, `ease −= 0.2` |

Clamp `ease` to [1.3, 2.8]. `due_at = now + interval_days`.

Route `/revise` shows due items. Cap the daily queue at 20 — an uncapped backlog after
a week off is how people quit. If more than 20 are due, show the 20 highest-priority
(by Phase 4 topic score) and say "20 of 47 due — the rest will keep."

## Phase 7 — Percentile comparison

Branch: `feat/percentile`

"You're in the top 22% of Telos users on Edexcel FM." Impossible for PMT to copy,
gets better as you grow.

- **Opt-in only** (`share_percentile_optin`), off by default, with a plain explanation
  that their anonymised score is included in cohort stats
- Suppress entirely when the cohort is under 20 users — anything less is both
  statistically meaningless and potentially deanonymising
- Never show anyone's absolute position or any other user's data
- Compute nightly into a materialised table; do not compute per request
- Show only above-median positions prominently. Below median, frame as improvement
  ("up 12 percentile points this month") rather than a rank. A student in the bottom
  decile being told so is a cancellation, not a motivation

## Phase 8 — Weekly parent report — CUT

Removed 2026-08-25 by the owner. Not deferred, not blocked: cut.

It is recorded here rather than deleted so nobody proposes it again as a new
idea. The original argument for it was revenue — it converts the person holding
the card — and the original cost was the consent machinery: double opt-in with
a parent confirmation link, one-click unsubscribe in every email, a revocable
settings toggle, stored confirmation timestamps, and all of it for a user base
that is mostly under 18. That cost does not go away, so if this is ever
revisited it starts from the same place.

The `parent_email` and `parent_report_optin` columns are gone from this
schema table, but they DO still exist on `users` in production — migration 001
created them both, and migrations are never rewritten. Verified 2026-08-25:
zero rows have either set, and no code outside that migration reads or writes
them. They are dead columns, not live data.

They are deliberately not dropped. Dropping a column is destructive and
irreversible, and two unused nullable columns on a three-row table cost
nothing. If they are ever removed it should be a numbered migration of its own,
decided on purpose rather than as a side effect of cutting a phase.

## Phase 9 — Shareable card export (free tier, this is the growth engine)

Branch: `feat/share-cards`

Free on purpose. It's marketing, not a feature.

Server-render PNGs with Pillow at two sizes: 1080×1920 (story) and 1080×1080 (post).

Card types: predicted grade + marks to next boundary; heatmap snapshot; streak /
papers-completed milestone.

Each card carries the Telos wordmark and a short URL. Store a token in `share_cards`
so a shared card resolves to a public read-only page — that page is the landing page
for everyone who sees the screenshot, so it needs a signup CTA.

Design brief: dark theme matching the app, one dominant number, high contrast, legible
at thumbnail size in a TikTok feed. Test by shrinking to 200px wide — if the number
isn't readable, it's wrong.

**Never include anything a user hasn't chosen to share.** No email, no full name unless
they opt in, no other users' data.

## Cross-cutting requirements

**Copyright.** Do not add any feature that stores or serves exam-board PDFs. Board
papers are linked out to the official Pearson/OCR pages, never hosted. Original mock
papers are ours and are fine to serve. If a phase seems to require hosting board PDFs,
stop and ask.

**Performance.** Predictions, percentiles and topic scores are precomputed. Dashboard
should issue a fixed number of queries regardless of how many papers a user has — check
with query logging, and add indexes where a page does more than ~10 queries.

**Neon.** Free tier scales to zero; `db.py` already pools connections. Don't open
connections outside `get_db()`.

**Analytics.** Log (server-side, no third-party tracker): upgrade prompt shown +
which feature, checkout started, checkout completed, cancel. Without this you can't
tell which feature is actually selling.

**Definition of done per phase:** migration applied cleanly to a fresh DB and to a
copy of prod; app boots; every nav item renders for both a free and a Pro test user;
new logic has unit tests; no `LIKE` on user input; no secrets committed.
